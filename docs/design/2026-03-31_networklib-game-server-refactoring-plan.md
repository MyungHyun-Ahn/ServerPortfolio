# 기획 노트

## 1. 배경
- 현재 저장소의 실행 프로젝트는 `EchoServer`이지만, MMORPG 서버 개발에 재사용 가능한 핵심 코드는 `NetworkLib`와 `includes`에 더 많이 남아 있다.
- 앞선 정적 리뷰에서 `NetworkLib`는 IOCP 기반 접속 처리, 세션 ID 발급, 콘텐츠 프레임 루프 같은 기반 구조를 이미 갖추고 있음을 확인했다.
- 반면 세션 슬롯 재사용, 콘텐츠 이동 시 세션 재검증, 종료 대기 방식처럼 게임 서버 코어로 계속 쓰기 전에 정리해야 할 수명주기/동시성 위험도 함께 확인됐다.
- 최근 `TestClient`를 추가해 로그인, 에코, heartbeat, 반복 접속/종료 시나리오를 검증한 결과 현재 구현이 즉시 무너지는 상태는 아니었지만, 이는 "기본 통신이 동작한다"는 근거일 뿐 "장기적으로 안전한 서버 코어다"를 뜻하지는 않는다.
- 또한 `MonitoringClientLib` 관련 `SO_UPDATE_CONNECT_CONTEXT` 오류 로그는 모니터링 서버 미구성 상태에서 발생한 별도 경로로 보이며, 현재 MMORPG 전환의 1차 범위에서는 코어 라이브러리 정리와 분리해서 다루는 편이 적절하다.

## 2. 목표
- `NetworkLib`를 Echo 샘플 서버 종속 코드에서 분리해, MMORPG 서버 개발의 기반이 되는 공용 서버 라이브러리로 정리한다.
- 네트워크 세션 수명주기, 콘텐츠 스레드, 패킷 전달 경계의 책임을 명확히 해 이후 월드/로비/인증 서버로 확장 가능한 구조를 만든다.
- 테스트 가능한 구조를 우선해, 현재 `TestClient` 기반 검증 시나리오를 리팩터링 이후에도 계속 재사용할 수 있도록 한다.
- 모니터링, 샘플 명령, 포트폴리오용 데모 로직은 코어에서 분리 가능한 선택 기능으로 정리한다.

## 3. 비목표
- 이번 단계에서 실제 MMORPG 게임 로직, 월드 시뮬레이션, 전투, 인벤토리, AI를 설계하거나 구현하지 않는다.
- 인증 서버, DB 서버, 로비 서버, 월드 서버의 멀티 프로세스 분산 구조까지 한 번에 확정하지 않는다.
- `NetworkLib` 전체를 새로 작성하지 않는다. 이미 검증 가능한 자산은 최대한 재사용하고, 위험한 경계부터 점진적으로 정리한다.
- 모니터링 서버 부재로 인한 LAN 클라이언트 오류는 별도 작업으로 남기고, 이번 기획서의 핵심 범위에는 포함하지 않는다.

## 4. 현재 구조와 관찰 근거
- 실행 시작점은 `EchoServer/Main.cpp`이며, 여기서 `CEchoServer`와 `MonitoringClientLib` 초기화가 함께 수행된다.
- 공용 서버 기능은 주로 `NetworkLib/CNetServer.cpp`, `NetworkLib/CNetSession.cpp`, `NetworkLib/CBaseContents.cpp`, `NetworkLib/CContentsThread.cpp`에 분포한다.
- 콘텐츠 이동과 세션 참조는 전역 서버 인스턴스와 세션 배열 접근에 강하게 의존한다.
- 정적 리뷰 문서 기준으로 우선 정리 후보는 다음과 같다.
  - 세션 해제 후 세션 배열 슬롯 정리 방식
  - `ProcessMoveJob()`의 세션 재검증 부족
  - `Stop()`의 busy-wait 종료 대기
  - 전역 상태와 샘플 애플리케이션 로직의 결합
- 동적 검증 기준으로는 `TestClient`를 통해 단일 접속, 다중 접속, 반복 에코, heartbeat, 짧은 접속/종료 반복까지는 정상 동작을 확인했다.

## 5. 제안 방향
### 5-1. 리팩터링 원칙
- 먼저 "안전성 보강"을 하고, 그 다음 "책임 분리"를 진행한다.
- 현재 외부 계약이 불명확한 전역 상태와 내부 포인터 공유를 줄이되, 한 번에 대규모 재작성하지 않는다.
- 게임 로직은 코어 위에 올라가는 상위 계층으로 보고, `NetworkLib`는 "세션 관리 + 패킷 전달 + 스레드 실행 기반"에 집중한다.
- 코어 라이브러리는 모니터링 유무와 관계없이 독립적으로 빌드/실행/테스트 가능해야 한다.

### 5-2. 목표 아키텍처 개요
- `NetworkLib`
  - IOCP 소켓 수락/송수신
  - 세션 풀 및 세션 ID 관리
  - 패킷 송수신 큐와 직렬화 버퍼
  - 콘텐츠 실행 스레드와 작업 전달
- 서버 애플리케이션 계층
  - 로그인/월드/로비 같은 도메인 콘텐츠
  - 패킷 디스패처
  - 세션별 플레이어 컨텍스트
  - 서버 설정, 운영용 명령, 모니터링 연결 여부
- 선택 기능 계층
  - 모니터링 클라이언트
  - 샘플 Echo 기능
  - 포트폴리오용 디버그 명령

### 5-3. 단계별 추진 계획
#### 1단계. 코어와 샘플 애플리케이션 경계 정리
- `EchoServer` 전용 로직과 `NetworkLib` 코어를 문서 기준으로 다시 분리한다.
- `MonitoringClientLib` 초기화, F1/F2 입력 기반 시스템 작업, Echo 패킷 흐름처럼 코어와 직접 관계없는 기능을 분리 후보로 표시한다.
- 결과물:
  - 코어에 남길 클래스 목록
  - 샘플 앱으로 이동하거나 삭제할 클래스 목록
  - 이후 `WorldServer` 골격에서 재사용할 최소 인터페이스 정의

#### 2단계. 세션 수명주기 안전성 보강
- 세션 슬롯 재사용과 해제 경계를 우선 보강한다.
- `m_arrPSessions` 접근 경로를 점검하고, 해제 시점과 참조 가능 시점을 코드 기준으로 다시 정리한다.
- 콘텐츠 이동 큐에서 세션 ID 재검증을 추가할지, 참조 카운트 계약을 강화할지 결정한다.
- 결과물:
  - 세션 해제/재사용 규칙 정리
  - 필요한 코드 수정
  - 회귀 검증 시나리오 업데이트

#### 3단계. 콘텐츠 계층 인터페이스 정리
- 현재 `CBaseContents`가 전역 서버와 세션 배열을 직접 만지는 구조를 줄인다.
- 콘텐츠 계층이 필요한 기능을 "세션 조회", "이동 요청", "패킷 송신", "접속 종료" 같은 인터페이스로 노출하는 방향을 검토한다.
- `void* objectPtr` 기반 이동 데이터는 장기적으로 타입이 드러나는 컨텍스트 구조체로 대체하는 방향을 잡는다.
- 결과물:
  - 콘텐츠 계층 책임 재정의
  - 콘텐츠-세션 간 최소 인터페이스 초안

#### 4단계. 패킷 처리 구조 일반화
- Echo 예제처럼 콘텐츠마다 직접 패킷을 해석하는 방식에서, 공용 헤더 검증과 디스패치 경계를 분리한다.
- 향후 MMORPG 패킷 체계로 확장할 수 있도록 공용 디스패처 또는 핸들러 등록 구조를 검토한다.
- 결과물:
  - 패킷 디스패처 설계 초안
  - Echo 패킷 처리의 이전 계획

#### 5단계. 새 서버 실행 프로젝트 골격 마련
- `EchoServer`를 바로 확장하지 않고, MMORPG 전환용 새 실행 프로젝트를 둔다.
- 초기 버전은 접속 수락, 세션 생성, 빈 콘텐츠 루프, 테스트용 최소 패킷만 제공한다.
- 결과물:
  - 새 실행 프로젝트 구조
  - 빌드 및 실행 기준 정리

## 6. 대안 비교
### 대안 A. `NetworkLib`를 점진적으로 정리하며 재사용
- 장점:
  - 이미 동작하는 IOCP/세션/버퍼/스레드 자산을 살릴 수 있다.
  - 포트폴리오 관점에서 "기존 구현을 검증하며 개선한 과정"을 남기기 좋다.
  - `TestClient`와 기존 Echo 흐름을 회귀 검증 기반으로 재사용할 수 있다.
- 단점:
  - 기존 전역 상태와 결합 구조를 점진적으로 뜯어내야 하므로 설계가 다소 보수적으로 진행된다.
  - 수명주기와 동시성 계약을 잘못 건드리면 회귀 위험이 크다.

### 대안 B. 새 서버 코어를 처음부터 재구성
- 장점:
  - 구조를 이상적으로 정리하기는 쉽다.
  - 샘플 코드 흔적과 레거시 제약을 빠르게 제거할 수 있다.
- 단점:
  - 현재 저장소의 핵심 자산을 버리게 된다.
  - 검증 기반이 약해지고, 포트폴리오로서도 기존 구현의 강점을 활용하기 어렵다.
  - 지금까지 확보한 테스트와 코드 리뷰 근거가 직접 이어지지 않는다.

### 선택 이유
- 현재는 대안 A가 더 적절하다.
- 근거는 이미 `NetworkLib` 기반 통신이 기본 시나리오에서 동작했고, 코드 리뷰를 통해 위험 지점도 특정된 상태이기 때문이다.
- 즉, "쓸 수 있는 기반을 증거 기반으로 정리해 나가는 방식"이 현재 저장소와 목표에 더 잘 맞는다.

## 7. 검증 계획
- 빌드 검증
  - `Portfolio.sln` x64 Debug 빌드 유지
  - 리팩터링 이후에도 `NetworkLib`, 실행 프로젝트, `TestClient`가 함께 빌드 가능해야 한다.
- 기능 검증
  - 단일 클라이언트 로그인/에코/heartbeat
  - 다중 클라이언트 동시 접속
  - 짧은 접속/종료 반복
  - 세션 재사용 가능성이 높은 반복 라운드 테스트
- 로그 검증
  - Accept/Recv/Send/Disconnect 실패 로그 변화 확인
  - 세션 해제와 재사용 시점 로그 추가 여부 검토
- 문서 검증
  - 구조 변경이 있을 때마다 설계 문서와 코드 리뷰 문서를 함께 갱신한다.

## 8. 리스크
- 수명주기 리스크
  - 세션 해제 계약을 부분적으로만 수정하면 오히려 잠복 버그를 만들 수 있다.
- 구조 리스크
  - 코어와 샘플 앱 경계를 급하게 나누면 실제 필요한 책임까지 흩어질 수 있다.
- 테스트 리스크
  - 현재 `TestClient`는 TCP 게임 패킷 경로 중심 검증이라, 모든 동시성 문제를 재현하지는 못한다.
- 운영 리스크
  - 모니터링과 디버그 기능을 분리하는 과정에서 기존 로그/운영 편의 기능이 일시적으로 줄어들 수 있다.

## 9. 결론
### 확정된 사실
- `NetworkLib`는 MMORPG 서버 전환의 기반으로 재사용할 가치가 있는 수준의 네트워크/세션/콘텐츠 구조를 이미 갖추고 있다.
- 동시에 세션 수명주기와 콘텐츠 이동 경계에는 리팩터링이 필요한 위험 지점이 확인됐다.
- `TestClient` 기반 검증으로 최소 통신 경로는 동작함을 확인했으므로, 이제는 구조 정리와 안전성 보강 단계로 넘어갈 수 있다.

### 불확실한 가설
- 현재 세션 참조 계약이 부하가 더 큰 실제 게임 서버 시나리오에서도 충분히 안전한지는 추가 코드 수정과 검증이 필요하다.
- 콘텐츠 계층 인터페이스를 얼마나 얇게 만들 수 있는지는 실제 1차 리팩터링을 해보면서 조정이 필요하다.

### 다음 확인 항목
- 세션 슬롯 정리와 세션 재검증을 첫 번째 코드 수정 대상으로 확정할지 검토
- 코어와 샘플 애플리케이션 경계 목록을 실제 파일 단위로 정리
- `WorldServer` 같은 새 실행 프로젝트 골격을 언제 도입할지 결정
