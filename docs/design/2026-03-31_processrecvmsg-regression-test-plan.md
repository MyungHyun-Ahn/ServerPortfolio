# 기획 노트

## 1. 배경
- `CBaseContents::ProcessRecvMsg()` 경로는 겉보기보다 민감하며, 작은 본문 분리만으로도 로그인 응답 수신 실패가 재현됐다.
- 같은 변경을 원복하면 다시 정상 동작했으므로, 이 경로를 다시 수정할 때는 일반적인 빌드 확인만으로는 부족하다.
- 따라서 `ProcessRecvMsg()`에 손대기 전후로 반드시 돌려야 할 전용 회귀 테스트 묶음을 정의한다.

## 2. 목적
- `ProcessRecvMsg()` 관련 리팩터링이 로그인, 에코, 재스케줄, 세션 release 경로를 깨뜨리지 않는지 빠르게 판별한다.
- 테스트 순서와 성공 기준을 고정해, 이후 작업마다 같은 기준으로 비교 가능하게 만든다.
- "빌드는 되지만 런타임에서 실패하는 회귀"를 조기에 잡는다.

## 3. 적용 범위
- 적용 대상:
  - `NetworkLib/CBaseContents.cpp`
  - `NetworkLib/CBaseContents.h`
  - `NetworkLib/CNetServer.cpp`
  - `NetworkLib/CNetServer.h`
  - `EchoServer` 콘텐츠의 `OnRecv()` 호출 경계에 영향을 줄 수 있는 변경
- 제외 대상:
  - 문서 수정만 있는 경우
  - `ProcessRecvMsg()`와 무관한 UI/로그 문구 수정

## 4. 테스트 묶음
### 4-1. 필수 1차 테스트: 단일 로그인/에코 확인
- 목적:
  - 가장 먼저 로그인 응답 수신 실패 같은 즉시 회귀를 잡는다.
- 실행:
  - `Portfolio.sln` x64 Debug 빌드
  - `EchoServer` 실행
  - `TestClient --clients 1 --repeat 1 --hold-seconds 1 --heartbeat-ms 1000 --no-wait`
- 성공 기준:
  - 서버 접속 성공
  - 로그인 성공
  - 에코 1회 성공
  - heartbeat 전송 성공
  - 최종 출력 `모든 테스트가 성공했습니다.`

### 4-2. 필수 2차 테스트: 다중 클라이언트 기본 수신 확인
- 목적:
  - `m_umapSessions` 순회와 세션별 수신 처리에서 클라이언트 간 간섭이 없는지 확인한다.
- 실행:
  - `EchoServer` 실행
  - `TestClient --clients 10 --repeat 5 --hold-seconds 1 --heartbeat-ms 1000 --no-wait`
- 성공 기준:
  - 10개 클라이언트 전부 로그인 성공
  - 각 클라이언트의 에코 반복 성공
  - 최종 출력 `모든 테스트가 성공했습니다.`

### 4-3. 필수 3차 테스트: 짧은 유지 + 재스케줄 확인
- 목적:
  - `SendPQCS()` 재기동 경로와 수신 후속 처리 타이밍이 깨지지 않았는지 본다.
- 실행:
  - `EchoServer` 실행
  - `TestClient --clients 1 --repeat 5 --hold-seconds 3 --heartbeat-ms 1000 --no-wait`
- 성공 기준:
  - 로그인 성공
  - 에코 5회 성공
  - hold 구간 동안 heartbeat 전송 성공
  - 최종 출력 `모든 테스트가 성공했습니다.`

### 4-4. 권장 테스트: 짧은 접속/종료 반복
- 목적:
  - `ProcessRecvMsg()` 변경이 세션 release와 다음 접속 라운드에 영향을 주는지 확인한다.
- 실행:
  - `EchoServer` 실행
  - 아래 명령을 5라운드 반복
  - `TestClient --clients 20 --repeat 5 --hold-seconds 1 --heartbeat-ms 1000 --no-wait`
- 성공 기준:
  - 모든 라운드 성공
  - 서버 크래시 없음
  - 로그인 응답 수신 실패 없음

## 5. 실행 순서
1. 빌드
2. 필수 1차 테스트
3. 필수 2차 테스트
4. 필수 3차 테스트
5. 필요 시 권장 테스트

## 6. 실패 판정 기준
- 아래 중 하나라도 발생하면 회귀로 본다.
  - 로그인 응답 수신 실패
  - 에코 응답 실패
  - heartbeat 전송 이후 비정상 종료
  - 서버 크래시
  - 테스트 명령 종료 코드 비정상

## 7. 기록 원칙
- 테스트를 돌린 날짜, 실행 명령, 성공/실패 여부를 코드 리뷰 문서에 함께 남긴다.
- 실패 시 "어느 테스트 단계에서 처음 깨졌는지"를 반드시 기록한다.
- 원복으로 정상화됐는지도 같이 적는다.

## 8. 다음 사용 기준
- `ProcessRecvMsg()` 경로를 다시 수정할 때는 최소한 필수 1차, 2차, 3차 테스트까지는 반드시 수행한다.
- 권장 테스트는 구조 변경 범위가 넓거나 세션 release 경로까지 건드렸을 때 추가한다.

## 9. 현재 기준선 결과
- 실행 날짜:
  - 2026-03-31
- 수행 결과:
  - 필수 1차 테스트 통과
  - 필수 2차 테스트 통과
  - 필수 3차 테스트 통과
- 관찰 메모:

  - 이 결과를 `ProcessRecvMsg()` 경로 리팩터링 전의 정상 기준선으로 사용한다.

## 10. 결론
### 확정된 사실
- `ProcessRecvMsg()`는 전용 회귀 테스트 없이 다시 만지기엔 위험하다.
- 단일 로그인/에코 확인만으로도 실제 회귀가 잡힌 적이 있으므로, 가장 작은 테스트가 가장 먼저 필요하다.
