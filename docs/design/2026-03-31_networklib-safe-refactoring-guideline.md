# 기획 노트

## 1. 배경
- `NetworkLib`를 MMORPG 서버 코어로 정리하는 과정에서 `CBaseContents::ProcessRecvMsg()` 경로는 예상보다 민감한 구간으로 확인됐다.
- `CBaseContents.cpp` 내부에서 세션별 수신 처리 본문을 helper로 분리하는 작은 정리만 수행했을 때도 `TestClient` 기준 로그인 응답 수신 실패가 재현됐다.
- 같은 변경을 되돌리면 동일 조건에서 다시 정상 동작했으므로, 현재 시점에서는 이 경로를 구조 변경보다 관측과 문서화가 먼저 필요한 구간으로 봐야 한다.

## 2. 목적
- 앞으로 `NetworkLib` 리팩터링을 진행할 때 어떤 범위부터 손대야 안전한지 기준을 문서로 고정한다.
- 회귀가 발생한 민감 구간과, 이미 회귀 없이 통과한 안정 구간을 구분한다.
- 다음 코드 작업이 "작아 보이는 정리"여도 실제 동작을 깨뜨리지 않도록 순서를 제한한다.

## 3. 현재 기준
### 3-1. 안정 구간
- `ProcessMoveJob()` 경로
- 세션 가드 보강 경로
- `Stop()` 종료 대기 구조
- 코드 동작을 바꾸지 않는 문서화 작업

### 3-2. 민감 구간
- `ProcessRecvMsg()` 본문 구조
- `OnRecv()` 호출 경계
- `SendPQCS()` 재기동 시점
- `Disconnect()`와 release가 맞물리는 수신 실패 경로

## 4. 안전 진행 원칙
- `ProcessRecvMsg()`는 별도 회귀 테스트 묶음과 관측 로그 기준이 준비되기 전까지 구조 변경하지 않는다.
- 서버-콘텐츠 계층 인터페이스 정리는 수신 경로 밖의 책임부터 줄인다.
- 코드 변경은 항상 한 파일, 한 책임 단위로 나눈다.
- 리팩터링 후에는 최소한 아래 검증을 유지한다.
  - `Portfolio.sln` x64 Debug 빌드
  - `EchoServer` + `TestClient --clients 1 --repeat 1 --hold-seconds 1 --heartbeat-ms 1000 --no-wait`
- 작은 정리처럼 보여도 런타임 회귀가 나오면 즉시 원복하고 문서에 근거를 남긴다.

## 5. 다음 안전 작업 순서
1. `CBaseContents`의 이동/leave 경로처럼 이미 안정성이 확인된 코드부터 정리
2. `ProcessRecvMsg()`는 코드 변경 대신 호출 관계와 부수효과 문서화 유지
3. `WorldServer` 도입을 위한 최소 인터페이스 후보를 문서로 먼저 정리
4. 필요 시 실행 순서를 바꾸지 않는 관측용 로그 추가
5. 위 기준이 준비된 뒤에만 `ProcessRecvMsg()` 재시도

## 6. 완료 조건
- 팀 기준 문서로서 "어디까지는 바로 리팩터링해도 되고, 어디부터는 추가 검증이 필요한지"가 구분되어 있다.
- 이후 작업이 이 문서 순서를 따를 수 있도록 인덱스에 연결되어 있다.

## 7. 결론
### 확정된 사실
- 현재 리팩터링은 공격적으로 진행할수록 위험하다.
- 이미 통과한 작은 경로부터 누적하는 방식이 가장 안전하다.

### 다음 확인 항목
- `ProcessRecvMsg()` 전용 회귀 테스트 묶음 정의
- `OnRecv()` 부수효과를 호출 순서 기준으로 문서화
- `WorldServer` 골격 설계 문서 초안 작성
