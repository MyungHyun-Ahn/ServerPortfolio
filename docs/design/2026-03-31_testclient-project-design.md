# 설계 노트

## 1. 배경
- `NetworkLib` 수명주기 검토를 실제 접속/송수신으로 검증하려면 최소 기능의 테스트 클라이언트가 필요하다.
- 현재 저장소에는 서버 샘플인 `EchoServer`는 존재하지만, 서버를 외부에서 재현 가능한 방식으로 두드릴 독립 실행형 테스트 클라이언트는 없다.
- 서버 검증이 목적이므로, 테스트 클라이언트는 서버 코어와 과도하게 결합되지 않으면서도 기존 패킷 규약과 설정을 재사용해야 한다.

## 2. 목표
- 솔루션에 `TestClient` 콘솔 프로젝트를 추가한다.
- `ServerConfig.conf`, `EchoProtocol.h`, `CEncryption`, `CFileLoader`를 재사용해 서버와 같은 패킷 규약으로 통신한다.
- 로그인 요청과 에코 요청을 자동으로 수행해 기본 네트워크 검증 경로를 만든다.

## 3. 비목표
- 이번 단계에서 부하 테스트 전용 더미 클라이언트까지 만들지 않는다.
- MMORPG 전용 프로토콜을 새로 정의하지 않는다.
- `NetworkLib` 기반 비동기 클라이언트를 새로 구현하지 않는다.

## 4. 현행 구조
- 서버 샘플은 `EchoServer`가 `CS_GAME_REQ_LOGIN`, `CS_GAME_REQ_ECHO`, `CS_GAME_REQ_HEARTBEAT`를 처리한다.
- 패킷 규약은 `NetworkLib::Core::Utils::Net::Header`와 `MHLib::scurity::CEncryption`을 따른다.
- 설정은 UTF-16 LE 형식의 `EchoServer/ServerConfig.conf`를 `CFileLoader`로 읽고 있다.

## 5. 제안 설계
### 5-1. 개요
- `TestClient`는 블로킹 WinSock 기반의 얇은 콘솔 앱으로 구현한다.
- 네트워크 전송은 단순하게 유지하고, 패킷 헤더/암호화/프로토콜 타입/설정 파일은 기존 자산을 재사용한다.

### 5-2. 데이터 흐름
1. `TestClient`가 `ServerConfig.conf`에서 서버 포트, 패킷 키, 패킷 코드를 읽는다.
2. 설정의 서버 IP가 `0.0.0.0`이면 실제 접속 대상은 `127.0.0.1`로 보정한다.
3. 클라이언트는 로그인 요청을 전송하고 로그인 응답을 검증한다.
4. 이어서 에코 요청을 지정 횟수만큼 보내고, 응답의 계정 번호와 송신 시각을 검증한다.
5. 검증이 끝난 뒤 지정 시간 동안 연결을 유지하며 heartbeat를 주기적으로 보낸다.

### 5-3. 주요 타입 / 인터페이스
- 재사용 요소:
  `EchoProtocol.h`
  `MHLib::utils::CFileLoader`
  `MHLib::scurity::CEncryption`
  `NetworkLib::Core::Utils::Net::Header`
- 신규 요소:
  `TestClient::Config`
  `TestClient::Detail::BuildClientPacket()`
  `TestClient::Detail::ReceivePacket()`
  `TestClient::Detail::RunClientSequence()`

### 5-4. 스레드 / 락 / 생명주기 고려사항
- 최초 구현은 블로킹 소켓 기반으로 두고, 병렬 접속은 프로세스 내부 스레드로 확장한다.
- 각 스레드는 독립 소켓 하나를 사용하므로, 클라이언트 쪽에서는 복잡한 락을 도입하지 않는다.

### 5-5. 실패 처리
- 접속 실패, 송수신 실패, 응답 타입 불일치, 체크섬 불일치는 즉시 실패로 처리한다.
- 목적은 서버 안정성 검증이므로, 재시도보다 실패 지점을 빠르게 드러내는 쪽을 우선한다.
- 기본 실행 시 콘솔을 바로 닫지 않고 결과를 확인할 수 있게 대기한다.

## 6. 대안 비교
### 대안 A
- 내용:
  단순 WinSock 기반 콘솔 클라이언트를 만든다.
- 장점:
  서버 문제와 클라이언트 프레임워크 문제를 분리하기 쉽다.
  빌드와 디버깅이 단순하다.
- 단점:
  향후 대규모 부하 도구로 확장하려면 추가 작업이 필요하다.

### 대안 B
- 내용:
  `NetworkLib`를 재사용한 비동기 테스트 클라이언트를 만든다.
- 장점:
  라이브러리 재사용 폭이 더 크다.
- 단점:
  서버와 클라이언트가 같은 구조를 공유해 문제 분리가 어려워질 수 있다.
  초기 검증 도구로는 구현 비용이 크다.

### 선택 이유
- 이번 단계는 서버 검증 도구 확보가 우선이므로 대안 A를 채택한다.
- 대신 패킷 규약과 설정 파일은 최대한 기존 자산을 재사용해 중복을 줄인다.

## 7. 검증 계획
- 빌드 검증:
  `Portfolio.sln` x64 Debug 기준으로 `TestClient`와 `EchoServer`를 빌드한다.
- 기능 검증:
  `EchoServer` 실행 후 `TestClient` 1개 접속으로 로그인/에코 성공 여부를 확인한다.
- 부하 / 성능 검증:
  `--clients`, `--repeat` 옵션으로 소규모 병렬 접속을 확인한다.
- 로그 확인 포인트:
  서버의 Accept/Recv/Disconnect 로그
  클라이언트의 응답 검증 실패 메시지

## 8. 리스크
- 기술 리스크:
  `EchoServer`가 샘플 코드라 로그인 이후 도메인 처리에서 예상 외 제약이 있을 수 있다.
- 운영 리스크:
  설정 파일의 바인드 주소 `0.0.0.0`를 클라이언트 접속 주소로 그대로 쓰면 접속에 실패한다.
- 추후 가능성:
  이후 더미 클라이언트, 반복 시나리오, 지연/손실 측정 도구로 확장 가능하다.

## 9. 결론
### 확정된 사실
- 테스트 클라이언트는 서버 검증 속도를 높이는 데 필요하다.
- 현재 저장소에는 재사용 가능한 패킷 규약, 설정 로더, 암호화 유틸이 이미 존재한다.

### 가설 또는 불확실성
- 현재 `EchoServer`가 실제 실행 환경에서 `TestClient`의 로그인/에코 시나리오를 그대로 통과하는지는 빌드와 실행으로 확인해야 한다.

### 후속 작업
- 빌드 후 접속/응답 검증을 수행한다.
- 이후 필요하면 병렬 접속 수와 반복 횟수를 늘려 세션 재사용 문제를 재현한다.
