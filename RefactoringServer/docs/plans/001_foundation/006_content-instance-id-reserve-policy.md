# Content Instance ID Reserve 비트 정책

## 1. 목적
- 현재 `contentInstanceId` 비트 레이아웃에서 `reserve` 4비트를 그대로 유지한다.
- 지금 단계에서는 의미를 고정하지 않되, 나중에 분산 서버 구조에서 `serverId`로 사용할 수 있는 방향을 정리한다.

## 2. 현재 상태
- `FContentInstanceId`는 다음 비트 구성을 사용한다.
  - `contentId`: 16비트
  - `reserve`: 4비트
  - `sequence`: 44비트
- 현재 샘플 서버는 `reserve = 0`만 사용한다.
- 즉 지금은 `reserve`가 “예약된 비트”라는 의미만 가진다.

## 3. 왜 지금 의미를 고정하지 않는가
- 현재 프로젝트는 단일 서버/단일 프로세스 기준 검증 단계다.
- 이 시점에 `reserve`를 곧바로 `serverId`로 고정하면
  - 설정 경로
  - 운영 문서
  - 배포 단위
  - 로컬 테스트 규칙
  까지 한 번에 묶여 들어온다.
- 그래서 지금은 비트를 남겨두고, 분산 구조가 실제로 시작될 때 의미를 확정하는 편이 더 안전하다.

## 4. 분산 서버 구조에서의 유력한 사용안
- 가장 유력한 후보는 `serverId`
- 해석 예:
  - `contentId`: 어떤 콘텐츠 타입인지
  - `serverId`: 어느 서버/노드가 이 인스턴스를 소유하는지
  - `sequence`: 해당 서버 안에서 증가하는 인스턴스 값

## 5. `serverId`로 사용할 때 기대 효과
- 서버 간 `contentInstanceId` 충돌 방지
- 로그에서 ID만 보고 소유 서버를 빠르게 추적 가능
- 분산 라우팅이나 원격 참조 핸들에서 디버깅이 쉬워짐

## 6. 4비트 한계
- 4비트는 `0 ~ 15`, 총 16개 값만 표현 가능하다.
- `0`을 로컬 단일 서버 기본값으로 둘 수는 있지만, 실제 분산 구조에서는 아래를 먼저 결정해야 한다.
  - `0`을 유효한 서버 ID로 쓸지
  - 운영 서버 수가 16개를 넘을 가능성이 있는지
  - `serverId`와 `nodeId`를 같은 의미로 볼지

## 7. 전환 시 검토 항목
- `reserve`를 `serverId`로 해석하는 시점
- 서버 설정값 또는 런타임 설정으로 `serverId`를 어디서 받을지
- 테스트 환경에서 기본값을 무엇으로 둘지
- 로그와 문서에서 `reserve`라는 이름을 `serverId`로 바꿀지

## 8. 현재 결론
- 지금은 `reserve`를 그대로 유지한다.
- 분산 서버 구조가 실제 범위에 들어오면, 이 4비트를 `serverId`로 전환하는 것이 1순위 후보다.
- 다만 그 전까지는 이름과 의미를 섣불리 고정하지 않는다.
