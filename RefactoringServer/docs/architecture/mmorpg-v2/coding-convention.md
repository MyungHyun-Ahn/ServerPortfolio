# 기획 노트

## 1. 목적
- 2세대 MMORPG 서버는 기존 포트폴리오 코드 스타일과 의도적으로 분리한다.
- 새 디렉터리와 새 솔루션에서 사용할 코딩 규칙을 먼저 고정해, 이후 구현이 누적되어도 스타일이 흔들리지 않게 한다.
- 내가 작성한 코드를 사용자가 이해하고 유지보수하기 쉽도록, 이름만 보고 역할과 소유권을 추측할 수 있게 만든다.

## 2. 네이밍 규칙
### 2-1. 타입 접두사
- `F`: 소유권과 동작을 가진 일반 클래스
- `I`: 인터페이스
- `S`: 값 전달용 구조체 또는 설정 구조체
- `E`: enum
- `T`: 템플릿

### 2-2. 함수와 변수
- 타입, 함수, enum 값은 `PascalCase`
- 지역 변수와 매개변수는 `camelCase`
- 멤버 변수는 `m_` 접두사 사용
- 정적 상수는 `kPascalCase`

### 2-3. 파일명
- 타입 이름과 파일명을 맞춘다.
- 한 파일에 한 주요 타입을 원칙으로 한다.
- 예시:
  - `ITransportServer.h`
  - `FIocpTransportServer.cpp`
  - `SServerConfig.h`

## 3. 설계 규칙
- 네트워크 계층은 인터페이스를 먼저 정의하고, 구현체는 `IOCP`, `RIO`, `boost.asio` 별로 분리한다.
- 도메인 계층은 네트워크 구현체에 직접 의존하지 않는다.
- 구현체를 바꿀 수 있는 경계에서는 반드시 `I*` 인터페이스를 통과한다.
- 전역 변수는 만들지 않는다. 정말 필요하면 명시적 singleton 대신 수명주기를 소유하는 상위 객체가 보유한다.

## 4. 동시성 규칙
- 코어 경로에서는 `std::mutex` 대신 원자 연산과 메시지 큐를 우선 검토한다.
- 공유 상태는 최소화하고, 가능하면 단일 작성자 모델로 이동한다.
- 세션 식별자는 재사용 충돌을 피하기 위해 `slot + generation` 형태를 기본으로 한다.

## 5. 코드 설명 규칙
- 코드 주석은 한국어로 작성한다.
- 무엇을 하는지보다 왜 이렇게 분리했는지, 어떤 경쟁 조건을 피하려는지 적는다.
- 외부 제약이 있는 경우 예를 들면 Windows API 제약을 함께 적는다.

## 6. 적용 범위
- `NextGenServer/` 아래 새 솔루션과 새 프로젝트에 적용한다.
- 기존 `NetworkLib`, `EchoServer`, `WorldServer`에는 소급 적용하지 않는다.
