# 기획 노트

## 1. 배경
- 현재 `NetworkLib`는 IOCP 기반 서버 코어, 콘텐츠 프레임, 세션 관리 경험을 담고 있어 포트폴리오와 리팩터링 실험 대상으로는 충분한 가치가 있다.
- 다만 `CNetServer`, `CBaseContents`, `CContentsThread` 사이 결합이 강하고, `ProcessRecvMsg()`처럼 민감한 경계를 작은 수정만으로도 깨뜨릴 수 있어 장기 확장형 MMORPG 서버 코어로는 한계가 보인다.
- 사용자 요구사항의 핵심 컨셉은 `락을 쓰지 않고 Interlocked 계열과 메시지 전달로 동기화하는 서버`이며, 이 방향은 2세대 구조에서도 유지하고 싶다.

## 2. 목표
- `NetworkLib`의 장점을 참고하되, 2세대 서버는 MMORPG 확장을 전제로 처음부터 경계를 분리해 설계한다.
- 네트워크 코어는 `lock-free` 또는 `single-writer` 원칙을 유지하고, 게임 로직은 메시지 전달 기반으로 확장한다.
- 인증, 로비, 월드, 비동기 DB 반영이 섞이더라도 세션 수명주기와 게임 오브젝트 수명주기가 뒤엉키지 않게 만든다.

## 3. 비목표
- 모든 계층을 순수 lock-free로 구현하는 것을 목표로 삼지 않는다.
- 처음부터 멀티 월드, 멀티 리전, 대규모 분산 배포까지 한 번에 해결하려 하지 않는다.
- 현재 `WorldServer` 골격을 억지로 최종 구조까지 확장하지 않는다.

## 4. 핵심 설계 원칙
### 4-1. 네트워크 코어는 무락 지향
- IOCP 워커는 소켓 I/O 완료 처리, 송수신 버퍼 전이, 세션 참조 관리에만 집중한다.
- 세션 식별은 `sessionId + generation` 형태로 설계해 재사용 슬롯 충돌을 줄인다.
- 세션 공개 API는 원자적 상태 전이와 메시지 큐 적재까지만 담당한다.

### 4-2. 게임 로직은 단일 작성자 모델
- 한 플레이어, 한 맵 shard, 한 채널의 상태는 특정 로직 스레드 또는 actor가 단독 소유한다.
- 다른 스레드는 직접 상태를 수정하지 않고 메시지로 요청한다.
- 이 구조를 통해 게임 상태 갱신은 락 대신 `소유권`으로 보호한다.

### 4-3. 계층 분리
- `transport`: IOCP, 세션, 송수신, 패킷 파서
- `gateway`: 패킷 디스패치, 인증 결과 라우팅, 연결 상태 이벤트
- `domain`: 플레이어, 월드, 전투, 채팅, 인벤토리 같은 게임 로직
- `infra`: DB 작업, 로그, 메트릭, 설정, 운영 도구

### 4-4. 프로토콜과 도메인 분리
- 패킷 타입과 도메인 명령은 1:1로 고정하지 않는다.
- 네트워크 입력은 `command` 또는 `event`로 변환한 뒤 도메인 계층으로 넘긴다.
- 도메인 결과는 다시 `outbound event`로 변환해 전송 계층으로 돌린다.

## 5. 제안 구조
### 5-1. 서버 구성
1. `AuthServer`
2. `LobbyServer`
3. `WorldServer`
4. `DbWorker` 또는 `DbService`
5. 공용 `NetCore` 라이브러리
6. 공용 `Shared` 라이브러리

### 5-2. 모듈 역할
- `NetCore`
  - IOCP, 세션, 송수신 버퍼, lock-free queue, 타이머 큐
- `Gateway`
  - 패킷 디코딩, 세션 인증 상태, 서버 간 라우팅
- `GameDomain`
  - 플레이어 상태, 맵 shard, AI, 스킬, 아이템
- `Infra`
  - DB, 설정, 로깅, 모니터링, 운영 명령

### 5-3. 스레드 모델
- `I/O Worker Thread`
  - 소켓 완료 통지 처리
- `Logic Thread`
  - shard 또는 actor 단위 상태 갱신
- `DB Completion Thread`
  - 비동기 DB 결과를 logic queue로 전달
- `Timer Thread` 또는 `Frame Scheduler`
  - 정기 tick, timeout, delayed event 발생

## 6. 데이터 흐름
1. 클라이언트 패킷 수신
2. IOCP 워커가 패킷 프레이밍과 검증 수행
3. gateway가 패킷을 내부 명령으로 변환
4. 대상 logic queue에 메시지 적재
5. logic thread가 상태를 단독 갱신
6. 응답 또는 브로드캐스트를 outbound queue에 적재
7. I/O 워커가 실제 송신 수행

## 7. 현재 코드에서 가져갈 것과 버릴 것
### 7-1. 재사용 후보
- IOCP 운용 경험
- 세션 식별과 참조 관리 아이디어
- `TestClient` 검증 루프
- 문서화와 회귀 테스트 기준

### 7-2. 참고만 할 것
- `CBaseContents` 중심 전역 접근 구조
- 세션 배열 직접 접근 패턴
- Echo 호환 패킷을 중심으로 한 실행 프로젝트 구조

### 7-3. 새로 설계할 것
- 세션 핸들 모델
- 패킷 디스패치 계층
- shard/actor 기반 로직 실행 구조
- DB 반영과 게임 상태 반영 사이의 경계

## 8. 단계별 추진안
### 8-1. 1단계
- `NetCore`와 `WorldServer` 골격을 분리한다.
- `TestClient`가 새 설정과 새 프로토콜 초안에 붙을 수 있게 보강한다.

### 8-2. 2단계
- `Lobby/World` 경계를 문서와 코드로 분리한다.
- 플레이어 세션과 플레이어 엔티티를 별도 수명주기로 분리한다.

### 8-3. 3단계
- shard 단위 logic thread와 메시지 큐를 도입한다.
- DB 결과와 외부 이벤트를 logic queue를 통해서만 반영한다.

## 9. 리스크
- lock-free를 너무 넓은 범위에 강제하면 디버깅 난도가 급격히 올라간다.
- 게임 로직에 직접 원자 연산을 과도하게 사용하면 코드 가독성과 검증 가능성이 떨어진다.
- 초기에는 `single-writer`와 `message passing`이 오히려 더 중요한데, 이를 무시하면 기존 구조의 한계를 반복할 수 있다.

## 10. 결론
### 확정된 사실
- `Interlocked` 중심의 무락 컨셉은 2세대 설계에서도 유지 가능하다.
- 다만 전체 시스템을 순수 lock-free로 밀어붙이기보다, `네트워크 무락 + 로직 단일 소유권` 구조가 더 현실적이다.

### 가설 또는 불확실성
- 실제 월드 규모와 동시 접속 목표에 따라 shard granularity와 queue 구조는 바뀔 수 있다.

### 후속 작업
- `NetCore`와 `GameDomain` 모듈 경계 초안 작성
- 세션 핸들 모델과 메시지 큐 인터페이스 초안 작성
- `WorldServer`를 임시 Echo 호환 구조에서 `Lobby/World` 진입 구조로 분리
