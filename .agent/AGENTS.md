# AGENTS.md

이 저장소는 **Windows + MSVC 기반 C++ 게임 서버 포트폴리오** 저장소다.
Codex는 작업 전 이 문서를 우선 준수하고, 세부 문서 형식은 `.codex/templates/`의 마크다운 템플릿을 참고한다.

## 1. 기본 원칙
- 항상 **근거 기반**으로 작업한다.
- 확인되지 않은 동작, 의도, 요구사항은 사실처럼 단정하지 않는다.
- 추론이 필요한 경우에는 코드/빌드 로그/문서/호출 관계 등 **관찰 가능한 근거**를 먼저 제시한다.
- 모르면 지어내지 말고 `불확실함`, `확인 필요`, `근거 부족`을 명시한다.
- 변경은 **최소 범위**로 수행하고, 주변 스타일과 규칙을 존중한다.
- 임시방편보다 **재현 가능성**, **디버깅 가능성**, **운영 안정성**을 우선한다.

## 2. 기술 스택 가정
- 플랫폼: Windows
- 컴파일러: MSVC
- 프로젝트 형식: `.sln`, `.vcxproj` 우선
- 언어: C++
- 도메인: 게임 서버 / 네트워크 / 동시성 / DB 연동 가능성 고려

## 3. 작업 시작 절차
1. 먼저 솔루션/프로젝트 구조를 확인한다.
2. `README`, `docs/`, 기존 설계 문서, 빌드 스크립트, 테스트 코드를 우선 확인한다.
3. 빌드/실행/테스트 방법이 문서에 있으면 그 절차를 따른다.
4. 문서가 부족하면 실제 프로젝트 파일과 명령으로 확인 가능한 사실만 사용한다.
5. 큰 변경 전에는 작업 가정과 범위를 짧게 정리한다.

## 4. 구현 원칙
- 기존 코딩 스타일, 네이밍, include 구조, 오류 처리 패턴을 우선 따른다.
- C++ 기능은 저장소의 표준 버전과 현재 코드베이스 관례에 맞춰 사용한다.
- 불필요한 전면 리팩터링은 하지 않는다.
- 성능 민감 경로에서는 추가 할당, 불필요한 복사, 잠금 범위 확대를 주의한다.
- 멀티스레드 코드에서는 락 범위, 소유권, 생명주기, 경쟁 조건 가능성을 먼저 점검한다.
- 네트워크/DB/파일 I/O는 실패 가능성을 전제로 처리한다.
- 로그는 디버깅에 도움이 되는 정보만 남기고, 과도한 잡음은 피한다.

## 5. 주석 및 설명 규칙
- **코드 설명 주석은 한국어로 작성한다.**
- 주석은 "무엇을 하는지"보다 **왜 이런 선택을 했는지**, **어떤 제약이 있는지**, **어떤 위험을 피하려는지**를 우선 설명한다.
- 코드만으로 명확한 내용은 장황하게 주석 처리하지 않는다.
- 확인되지 않은 의도는 주석으로 단정하지 않는다.
- TODO/FIXME는 한국어로 작성하고, 가능한 경우 조건과 이유를 함께 적는다.

예시:
- 좋음: `// 세션 종료 직후 비동기 완료가 도착할 수 있으므로 생명주기 확인 후 처리한다.`
- 나쁨: `// 이 함수는 패킷을 처리한다.`
- 나쁨: `// 아마 서버 시작 시 항상 먼저 호출됨.`

## 6. 변경 검증 원칙
- 변경 후 가능한 범위에서 **빌드 또는 정적 검증**을 수행한다.
- 검증을 못 한 경우에는 무엇을 검증하지 못했는지 명확히 남긴다.
- 버그 수정 시 가능하면 재현 조건, 원인, 수정 포인트, 남은 리스크를 함께 정리한다.

## 7. 문서 생성 규칙
코드 작업 시 아래 상황에서는 관련 문서를 **함께 생성하거나 갱신**한다.

### 7-1. 코드 리뷰 문서
다음에 해당하면 `docs/code-review/` 아래 문서를 만든다.
- 구조가 복잡한 변경
- 동시성/메모리/수명주기/예외 흐름 관련 변경
- 성능 또는 안정성 영향이 있는 변경
- 리뷰어가 판단 근거를 알아야 하는 변경

파일명 예시:
- `docs/code-review/2026-03-31_session-lifecycle-review.md`

형식:
- `.codex/templates/CODE_REVIEW_TEMPLATE.md`

### 7-2. 기획/설계 문서
다음에 해당하면 `docs/design/` 아래 문서를 만든다.
- 신규 기능
- 시스템 구조 변경
- 데이터 흐름 변경
- 운영/배포/확장성 고려가 필요한 작업

파일명 예시:
- `docs/design/2026-03-31_matchmaking-queue-design.md`

형식:
- `.codex/templates/DESIGN_NOTE_TEMPLATE.md`

### 7-3. 트러블슈팅 문서
다음에 해당하면 `docs/troubleshooting/` 아래 문서를 만든다.
- 빌드 오류 해결
- 런타임 크래시/데드락/성능 저하 분석
- 환경 설정 문제 해결
- 재발 방지 가치가 있는 디버깅 사례

파일명 예시:
- `docs/troubleshooting/2026-03-31_msvc-link-error-troubleshooting.md`

형식:
- `.codex/templates/TROUBLESHOOTING_TEMPLATE.md`

## 8. 문서 작성 원칙
- 문서는 **한국어**로 작성한다.
- 추측보다 **근거, 로그, 호출 경로, 재현 절차, 측정값**을 우선 적는다.
- 독자가 바로 재현/검증할 수 있도록 명령, 경로, 입력 조건을 남긴다.
- 결론에는 반드시 **확정된 사실**, **불확실한 가설**, **다음 확인 항목**을 구분한다.

## 9. 응답 방식
작업 완료 보고에는 가능하면 아래를 포함한다.
- 무엇을 바꿨는지
- 왜 바꿨는지
- 어떤 근거로 판단했는지
- 무엇을 검증했는지 / 못 했는지
- 생성 또는 갱신한 문서 목록

## 10. 피해야 할 행동
- 근거 없이 아키텍처를 재구성하지 않는다.
- 확인되지 않은 성능 최적화를 단정적으로 넣지 않는다.
- 관련 없는 파일까지 광범위하게 건드리지 않는다.
- 빌드/런타임 영향이 큰 설정을 설명 없이 바꾸지 않는다.
- 영어/한국어 주석 스타일을 뒤섞지 않는다. 특별한 사유가 없으면 설명 주석은 한국어를 사용한다.
